## 1. 回归：L1 通知记账不能坏

- [ ] 开「通知使用权」→ 采集状态显示**绿点「正常监听中」**
- [ ] 支付宝 / 微信付一笔 → 自动记一笔 + 「已记账」通知
- [ ] 同一条通知被系统重发 → 诊断「同条通知重发」，**不重复记账**
- [ ] 收到营销 / 账单提醒类带金额通知 → 诊断「已忽略」或「识别到通知但没抽到金额」，**不记账**
- [ ] 关掉「自动采集记账」开关 → 不再新增任何账单

## 2. L2 权限与状态卡

- [ ] 无障碍**未开** → 卡片橙点「未开启（不影响自动记账，只影响分类准度）」+「去开启」
- [ ] 点「去开启」→ 进入系统无障碍设置页，列表里能看到「小凯记账 · 分类识别」
- [ ] 返回 App → 卡片自动变绿点「正常识别中」（无需重启 App）
- [ ] 系统设置里权限仍勾选、但强杀进程 → 卡片变红点「已开启但识别服务未连接」+「去重新开启」
- [ ] 引导步骤「开启分类识别（无障碍）」标记为**已完成**

## 3. L2 补分类（前向命中：通知落账时就已经定了分类）

- [ ] 美团下单付款 → 分类是**早午晚餐(21)**
- [ ] 滴滴行程付款 → 分类**打车(27)**
- [ ] 瑞幸 / 星巴克付款 → 分类**咖啡奶茶(24)**
- [ ] 淘宝 / 京东 / 拼多多付款 → 分类**购物(3)**
- [ ] 叮咚买菜付款 → 分类**烹饪食材(25)**
- [ ] 「最近处理」显示 `已补全分类` 或 `已自动补记一笔`，并附截断后的「识别到的内容」

## 4. L2 补分类（后向回填：先落「其他」，再被信号改回来）

> 这是本次改动的核心能力

- [ ] ① 关掉无障碍开关 → ② 支付宝付一笔 → ③ 该笔分类落「其他(12)」
- [ ] ④ 5 分钟内打开无障碍 → ⑤ 打开该笔的订单 / 商户详情页（页面含金额）→ ⑥ 「最近处理」= **`已补全分类`**，账单分类由「其他」变为具体分类
- [ ] 该笔账单的**金额 / 时间 / 来源**都没变，且**没有变成两笔**
- [ ] 关掉通知使用权只留无障碍时：L1 的账单与诊断**完全不动**（两条通道互不干扰）

## 5. L2 补记账（建账 / 宽限期 / 安全放弃）

- [ ] **建账**：① 临时关掉「通知使用权」（让 L1 完全不出手）→ ② 开无障碍 → ③ 美团下单付款 → ④ 等约 25 秒 → ⑤ 多出**一笔**账，来源「分类识别」，分类**早午晚餐**
- [ ] **宽限期防重**：通知使用权 + 无障碍都开 → 扫码付一笔 → 最终**只有一笔**账（信号早到也会等 20 秒复核，转为补分类）
- [ ] **抽不到金额不建账**：停在商户首页等无金额页面 → 「最近处理」= `识别到内容，但没抽到金额`，**不新增账单**
- [ ] **多候选放弃**：5 分钟内用同一商户付两笔**同额**（间隔 >3 秒，避开秒级去重）→ 打开该商户页面 → 期望 `附近有多笔，未自动处理`，**既不回填也不建账**

## 6. 确认卡片

**前置（唯一条件）**：

- [ ] 引导页「分类识别（无障碍）」卡显示 **「正常识别中」**（绿点）—— 卡片靠无障碍服务挂出
- [ ] 点「**测试确认卡片**」→ 卡片直接盖在当前页面上
- [ ] 卡片下方「**卡片投递结果**」显示 `DELIVERED`

> 为什么不需要任何权限：卡片用 `TYPE_ACCESSIBILITY_OVERLAY` 类型的窗口承载，
> 只要本应用的无障碍服务在运行即可，无需悬浮窗权限。
> 若投递失败，「卡片投递结果」会直接给出原因（`NO_SERVICE` / `NO_BILL` / `FAILED: …`）。
>
> ⚠️ 重装 APK 会让系统**自动停用**无障碍服务，需重新到
> 「系统设置 → 无障碍 → 小凯记账 · 分类识别」开关一次才会重新绑定。

- [ ] CREATED / ENRICHED 之后**卡片自动弹出**，且不离开当前 App（半透明浮层）
- [ ] 卡片内容正确：金额带 `-`、分类名、时间、来源标签
- [ ] 点**分类行**或「改分类」→ 跳进记账编辑页，且是正确的那一笔
- [ ] 点「撤销这笔」→ 账单被删除，卡片关闭
- [ ] 点卡片外空白 → 卡片关闭，**账单保持不变**（这是关闭，不是取消）
- [ ] 同一笔只弹一次
- [ ] 通知落账（L1）**不弹卡片**（卡片只服务于 L2 建账 / 回填）

## 7. 安全边界（这几条**绝不能**违反）

- [ ] **手动记账**的分类在任何情况下都不被自动改写
- [ ] 已命中分类的账单（如通知正文写了「餐饮」）不被回填改写
- [ ] 回填只改「分类 + 更新时间」，金额 / 时间 / 来源 / 去重键一律不变
- [ ] 非白名单 App 的页面文本绝不被读取
      （白名单：支付宝 ×2、微信、美团 ×2、饿了么、叮咚、滴滴、淘宝、京东、拼多多、瑞幸、星巴克）
- [ ] 关闭无障碍开关后，无障碍通道**零产出**（不读节点、不投信号）

## 8. 重点观察与已知限制

| # | 项 | 说明 |
|---|---|---|
| 1 | **卡片只能靠无障碍悬浮层，不能靠启动 Activity** | 官方《活动安全性》列的后台启动 Activity 豁免共 8 条，**没有「无障碍服务」** —— 早先靠它拉起半透明 Activity，真机上一张卡片都没弹出来过，且系统是**静默拦截**（不抛异常）。正确做法是 `WindowManager.addView` + `TYPE_ACCESSIBILITY_OVERLAY`（不需要任何权限，小黑记账同款：其悬浮窗权限是 denied，面板照常显示）。**另一个坑**：`WindowManager` 必须取自**无障碍服务自己的上下文**，用 Application 上下文会抛 `BadTokenException: token null is not valid` |
| 2 | **L2 建出的账通常没有账户** | 它的来源包名多是商户 App（美团 / 京东），`AccountRouter` 会落空。这符合事实（账户本就是支付宝 / 微信 / 银行卡），**不是 bug** |
| 3 | **诊断文本会存下页面原文（200 字）** | 设计上如此（便于事后复盘「为什么分错了」），但它可能包含聊天、订单等私密内容并落进 DataStore。**建议下一轮评估**：是否只在「文本已命中分类词」时才存原文，或对未命中内容只存长度摘要 |
| 4 | L3 截图识别 | 本轮未实现，无需授予任何媒体权限 |

**已修复的闪退**（2026-09-19）：

```
java.lang.IllegalArgumentException: Key "accessibility" was already used.
```

`LazyColumn` 中新增卡片的 `key = "accessibility"` 与引导步骤 `GuideStep.id = "accessibility"` 重复。
已改为：卡片 key 用 `category_title` / `category_card`，步骤 key 统一加前缀 `step_`，
让两个名字空间不再可能撞车。

**已修复的重复记账**（2026-09-19，高危）：

真机数据：`id=100`（NOTIFICATION）与 `id=101`（ACCESSIBILITY）同金额 `5584` 同一笔。
三道防线全部失效：

| 防线 | 失效原因 |
|---|---|
| `DedupKey` 唯一索引 | 秒桶 —— 两条投递相隔 **5377ms**，落在不同秒格 |
| `existsInWindow` | 窗口 **3000ms** —— 5377ms 超出 |
| 宽限期复核 | 只查 `categoryId IN (12,18,20)`；而通知那笔**已被信号自己分成 21**，于是「看不见」它 → 误判无账可配 → 建账 |

修法：候选查询不再按分类过滤（`BillDao.findAutoBillsInWindow`），回填候选由决策器在内存里筛；
新增「这笔是否已记过」判定 —— 窗口内存在**同金额**的自动来源账单即判 `DUPLICATE`，绝不建账。
新增 3 个回归用例，其中一条正是复刻上述真机形态。

**已修复的卡片投递**（2026-09-19）：

卡片一次都没弹过。排查过程（每一步都有设备证据）：

| 环节 | 证据 |
|---|---|
| 小黑记账到底用了什么 | `appops get com.xhs.xiaohei SYSTEM_ALERT_WINDOW` = **ignore**（确实没开悬浮窗），但其窗口列表里有 `ty=ACCESSIBILITY_OVERLAY` → 用的是无障碍悬浮层 |
| 为什么 Activity 方案不行 | 官方豁免 8 条里没有「无障碍服务」，系统静默拦截 |
| 改用悬浮层后第一次仍失败 | logcat：`WindowManager$BadTokenException: token null is not valid`（Application 上下文的 token 是 null） |
| 改用服务上下文后又崩 | `IllegalStateException: Composed into the View which doesn't propagate ViewTreeSavedStateRegistryOwner` —— Compose 要求 `LifecycleOwner` + `SavedStateRegistryOwner` + `ViewModelStoreOwner` **三个宿主都在**，缺一个就崩 |
| 最终修法 | ① `WindowManager` 取自无障碍服务上下文；② ComposeView 装上三个宿主；③ 投递结果写进诊断 |

**已验证**（设备证据，非推断）：

```
mOwnerUid=... package=com.kai.billofkai appop=CREATE_ACCESSIBILITY_OVERLAY
mAttrs={(0,0)(fillxfill) ty=ACCESSIBILITY_OVERLAY fmt=TRANSLUCENT}   ← 我们的悬浮卡片已建立
服务：Service[label=小凯记账 · 分类识别, capabilities=1 ...] 已绑定
崩溃缓冲区：空
投递结果：DELIVERED
```

另外记录几个排查时会踩的坑：

- **重装 APK 会让系统停用无障碍服务**，且 vivo 不会仅凭 `settings put` 重新绑定 ——
  必须在「系统设置 → 无障碍」里手动开关一次；绑定生效可能要等 20~30 秒。
- 引导页在点了「测试确认卡片」后会多出一行提示，**布局会下移**，
  若要脚本化验证必须重新取按钮坐标，不能复用旧坐标。
- **`rootInActiveWindow` 只有焦点窗口**：微信账单详情（小程序页 `AppBrandUI00`）把
  「商户名 + 金额」画在另一个窗口里，只读焦点窗口会**整块漏掉金额**——
  真机表现为：系统 `uiautomator` 能看到 `-1.00`，我们的识别内容里却始终没有，
  于是信号抽不到金额、无法独立成账。
  修法：`accessibilityFlags` 加 `flagRetrieveInteractiveWindows`，
  抽取时优先取「与事件同包名的最上层窗口」的根，取不到再退回焦点窗口。
- 同理，`AccessibilityWindowInfo` **没有 packageName**，只能从 `window.root.packageName` 取。
